OSAHI

Four parts of the lifecycle

Open MCP router

Discovery, routing, and authorization for tool endpoints. The reasoning loop does not know where the tool lives.

Virtual memory

Scratchpad, episodic cache, cold storage. Prune the context. Keep the log.

GenAI telemetry

OpenTelemetry semantic conventions on every step: tokens, latency, tool sequence, errors.

Event-sourced orchestrator

Immutable history. Pause and resume. Replay a failure without erasing it.

OSAHI

What is running, and what we standardize

Now
Standard

MCP router

A tool is requested, decided, and invoked only after allow. A remote HTTP tool uses that same path.

Any MCP endpoint registers once and the loop does not change.

Calendar and mail can move to another service and the decision event stays.

Virtual memory

An L1 scratchpad compacts when the budget overflows, and the trajectory is not shortened.

Episodic cache and cold storage are further tiers. Dropped context is summarized, not deleted from the log.

Telemetry

Model and tool outcomes carry gen_ai and osahi attributes on the event.

Those attributes export through OpenTelemetry without a second schema.

Orchestrator

An append-only log, checkpoints, retry / rollback / escalate, and human pause and resume. Replay uses recorded model and tool returns.

Any runtime can fold that log and recover the same way. The failed attempt stays.

OSAHI

Neutral interoperability and reliability
across models, tools, and runtimes

Models

Swap the model. Tool execution and memory stay.

Tools

Move calendar or mail to another service. The decision event stays.

Runtimes

Another loop emits the same record. Recovery and pause still read.

Reliability is checkpoint, pause, resume, and replay that keeps the failed attempt.
